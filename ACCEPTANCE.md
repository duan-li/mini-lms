# Mini-LMS technical assessment acceptance report

22 November 2026

**The application passes functional acceptance. Overall acceptance remains conditional on evidence of submission.** Students can sign up, sign in, sign out and manage their own consultations. Admins can page through all consultations in a read-only view. Both medium-priority security findings from the M6 review have fixes and regression tests on the verification branch. Of the 54 plan items, 52 have supporting evidence. The two open items concern the artifact received by Rippling and the time of submission. Concurrent requests for the same student and slot yield one success and one conflict. ## Security findings on the M6 baseline

| Priority and status | Finding and impact | Action and evidence |
| --- | --- | --- |
| Medium. Confirmation redirect. Fixed on the verification branch | After successful email OTP verification, the handler used the `next` query parameter as the redirect destination. Next.js accepts absolute URLs, so a valid confirmation could lead to an external phishing page. The review observed no account or token disclosure. | The fix allows specific internal destinations and falls back to the homepage. Regression tests cover allowed and rejected destinations. [M6 handler](https://github.com/duan-li/mini-lms/blob/10c50e6/app/auth/confirm/route.ts#L10), [Next.js redirect behavior](https://nextjs.org/docs/app/api-reference/functions/redirect) |
| Medium. List availability. Fixed on the verification branch | An authenticated student could write their own scheduled time directly through Supabase. The database checked that the time was in the future. PostgreSQL supports non-finite timestamps and years outside the browser's display range. The DTO passed the stored value to the table for formatting with Intl. Static review identified a risk that one such row could prevent a student or admin page from rendering. | The migration bounds newly assigned times and the UI supplies a fallback for an unreadable historical value. [M6 database rule and grants](supabase/migrations/20261121090200_consultation_rules.sql#L28), [PostgreSQL date/time types](https://www.postgresql.org/docs/17/datatype-datetime.html), [DTO](lib/services/consultation-dto.ts#L30), [admin table](components/admin/admin-consultation-table.tsx#L90), [formatter](lib/datetime.ts#L39) |
| Low. Input consistency. Open | The API trims names and reasons before storage. SQL checks the length of the trimmed value but stores the original text. Direct database writes can therefore store and return more characters than the documented field limit. JavaScript and PostgreSQL also differ in their default whitespace handling. | Normalize values or constrain their stored length in the database and test the boundary on both write paths. [API validation](lib/validation/consultation.ts#L7), [table constraints](supabase/migrations/20261121090100_consultations.sql#L8), [write grants](supabase/migrations/20261121090200_consultation_rules.sql#L103) |

**Request origins.** Booking mutations authenticate via cookies. The wrapper does not check the request Origin or a CSRF token. Cancellation requires a valid booking ID and accepts a request without a JSON body. The pinned Supabase SSR library defaults to `SameSite=Lax`. If a future deployment shares a site with an untrusted subdomain, same-site cookie rules alone would allow requests from distinct origins. A trusted-origin check on browser writes would address this condition. The review found no evidence of that deployment topology. [Auth wrapper](lib/api/with-auth.ts#L22), [cancel route](app/api/consultations/%5Bid%5D/cancel/route.ts), [session configuration](lib/supabase/server.ts), [locked dependencies](package-lock.json)

**Verified controls.** The API verifies sessions with `getUser` and uses the database role for route access. Queries and RLS both restrict ownership, and users cannot change their role field. Tests using real roles confirmed that students cannot read or modify another student's booking and an admin cannot edit its own pre-promotion booking. SECURITY DEFINER functions use an empty search path and protected columns have explicit grants. The application wrapper logs structured fields. Tests confirm that consultation reasons and upstream error details stay out of those logs. [Authentication and logging](lib/api/with-auth.ts), [role functions](supabase/migrations/20261121090000_profiles_and_roles.sql), [RLS tests](tests/integration/rls.test.ts), [log assertions](tests/unit/with-auth.test.ts#L94)

**Credentials and dependencies.** At review time, `npm audit` reported zero known dependency advisories at every severity. Git ignored `.env.local` and tracked only `.env.example` among environment files. A signature scan of history reachable from M6 found no matches for Supabase secrets, JWTs, common GitHub or AWS tokens, or private-key markers. The scan only covers those signatures. The application clients use public configuration. The seed includes working test credentials, including an admin password, for isolated local use. Exclude that seed from deployments. [Environment example](.env.example), [ignore rules](.gitignore), [runtime client](lib/supabase/server.ts), [local seed](supabase/seed.sql), [lockfile](package-lock.json)

**Daylight-saving gap.** With `TZ=Australia/Melbourne`, calling `localInputToIso` with `2027-10-03T02:30` returned `2027-10-03T03:30:00+11:00`. The requested wall-clock time falls in the spring-forward gap. The form accepts the adjusted time, which can change the student's intended appointment. Compare the converted date and time components with the input and ask the student to choose an existing local time when they differ. [Conversion](lib/datetime.ts#L14), [form validation](lib/validation/consultation.ts#L74), [date tests](tests/unit/datetime.test.ts)
